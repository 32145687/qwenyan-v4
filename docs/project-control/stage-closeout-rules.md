# 阶段收尾规则（永久执行）

> 适用范围：Qianyan 所有后续阶段/子阶段。
> 本文件是阶段收尾的最低强制清单；不得以“时间紧/测试通过/文档齐全”为由跳过。

## 1. 必须执行的九项

每次阶段完成后必须：

1. **对照 v3.1 总规划与功能列表**：确认本阶段属于哪个 Phase / 子阶段，是否满足依赖与 Completion Gate。
2. **按实际代码与验收证据标记功能状态**：禁止用计划/推断代替实际证据。
3. **更新对应开发工作区的阶段 MD**：只修改该工作区拥有的文档；不复制到其他工作区。
4. **同步总规划中的阶段进度与功能完成情况**：在 `docs/project-control/` 更新控制层；不改写 v3.1 正文或冻结契约。
5. **保留测试结果、已知限制和待验证事项**：不得只写“通过”。
6. **检查各开发工作区的 Git 状态**：路径、分支、HEAD、staged、modified、untracked。
7. **执行适当的 `git diff --check`**：在**实际修改的工作区**执行并记录 exit code。
8. **输出逐项 Completion Report**：区分已验证通过 / 部分验证 / 未验证 / 失败项。
9. **HARD STOP**：不自动进入下一阶段，不擅自 commit 或 push。

## 2. 自动化验收与 GUI 验收必须分开

- 自动化测试通过，只能证明自动化验收通过。
- GUI 交互未执行时，必须标记 `PENDING_VERIFICATION` 或 `NOT RUN`，不得写成 PASS。
- 不得用源码接线测试、Toast 文案测试或截图观察替代真实点击/输入验收。
- 如果环境阻止 GUI 自动化，记录阻断点、错误信息与退出状态；不得绕过安全策略。

## 3. 状态词

- `DONE`：实现与规定验收（含必要的 GUI/人工验收）均已成立。
- `IN_PROGRESS`：实现或验收尚未完成。
- `NOT_STARTED`：本阶段尚未开始。
- `BLOCKED`：存在明确阻塞，且已记录原因。
- `PENDING_VERIFICATION`：实现/自动化证据存在，但规定的验收未执行。
- `DEFERRED`：明确不在当前阶段实施，且有决策依据。

## 4. 文档与工作区边界

1. 同一文档多副本时，先确认权威所有者，只改所有者副本。
2. 不把 A/B/C/D 的文档随意复制进 MAIN；不把 D 审计文档当生产代码合并。
3. 不修改冻结的架构契约来“补齐”阶段状态。
4. 不为了统一文件名而覆盖、删除或重命名既有文档。
5. 发现规划与实际代码不一致：记录差异、证据、影响与建议；不擅自改写规划。

## 5. Git 安全

阶段收尾只允许必要的文档/代码修改（按当轮授权），并遵守：

- 不执行 `git reset --hard`、`git clean`、未经确认的 `restore/stash`；
- 不覆盖其他工作区的修改；
- 不删除/重建开发工作区；
- 不擅自 merge/cherry-pick；
- 不 commit/push，除非用户明确授权。

## 6. Completion Report 最低字段

1. 开发工作区实际状态（路径/分支/HEAD/staged/modified/untracked）。
2. 修改/新增文件清单。
3. 阶段/功能状态变更。
4. 自动化验收命令、exit code、测试数量、failures/errors/skipped。
5. GUI/人工验收状态；未执行项必须标注。
6. 已知限制与未验证项。
7. `git diff --check` 结果。
8. Schema/Migration 是否变化。
9. 是否 commit/push。
10. 下一阶段建议及其 v3.1 依据（只建议，不自动开始）。
